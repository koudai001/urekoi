# Technical Highlights

## 動的ルートの遷移パフォーマンス

- 課題: 動的データの取得完了まで画面遷移が待機する
- 工夫: `loading.tsx`で部分prefetchとストリーミングを有効化
- 効果: 共通UIを維持したまま、ローディングを即時表示

## 検索詳細の表示高速化

- 課題: 検索一覧から詳細へ遷移するたびに同じプロフィールを再取得していた
- 工夫: 一覧取得時にプロフィール単位でもTanStack Queryへキャッシュし、詳細画面と共有
- 効果: 通常遷移時のAPIリクエストをなくし、詳細を即時表示

## WebSocketとTanStack Queryによるキャッシュ設計

- 課題: メッセージやマッチ状態の更新ごとに発生する全件再取得と表示遅延
- 工夫: WebSocket接続を1本だけ維持し、受信データを複数のQueryキャッシュへ部分反映
- 効果: リアルタイム表示を維持しながら、通信量・API負荷・インフラコストを削減

## カード操作後の表示高速化

- 課題: 一覧・詳細間の遷移やLike・Skip後に発生するカードの再取得と状態消失
- 工夫: 共通layoutのProviderで画面遷移時も状態を維持し、アクション成功時はTanStack Queryへ操作結果を直接反映
- 効果: Providerの再マウントと一覧APIの再取得を防ぎ、操作後のカード状態を即時表示

## 画像表示の最適化

- 課題: プロフィール画像の再取得、転送量、レイアウトシフト
- 工夫: フロントエンドとバックエンドで`Cache-Control`を指定して画像を長期キャッシュし、更新時は新しいS3 keyを発行。あわせて`next/image`、`sizes`、遅延読み込み、LCP候補の先行読み込みを使用
- 効果: キャッシュによる画像リクエスト削減、表示幅に合う画像配信、LCP短縮、CLS防止

## k6負荷試験

- 認証フロー・WebSocketに対応できるためk6を採用(Vegeta等はリクエスト間の値の受け渡し不可)
- 発見: DBコネクションプールの上限未設定。負荷時にPostgres接続が枯渇

## プロフィール画像配信

- 課題: APIサーバーの画像転送負荷と、画像URL変更時のDB更新
- 工夫: presigned URLでストレージへ直接アップロードし、DBにはS3 keyだけを保存
- 効果: API負荷を抑え、配信ドメイン変更時のDB更新を不要化

## 検証環境の初回レスポンス改善

- 課題: コールドスタートとリージョン間通信による初回遅延
- 工夫: APIの常時起動、タイムアウト設定、Vercel FunctionとRenderのリージョン統一
- 効果: 初回アクセス時の待ち時間と長時間ブロックを削減
