# Technical Highlights

## 動的ルートの遷移パフォーマンス

- 課題: 動的データの取得完了まで画面遷移が待機する
- 工夫: `loading.tsx`で部分prefetchとストリーミングを有効化
- 効果: 共通UIを維持したまま、ローディングを即時表示

## WebSocketとTanStack Queryによるリアルタイム表示

- 課題: 新着メッセージごとの再フェッチによる表示遅延とAPI負荷
- 工夫: WebSocket接続を共通Providerで1本だけ維持し、受信データを複数のQueryキャッシュへ直接反映
- 効果: リロード不要の即時表示とAPIリクエスト削減

## TanStack Queryによるスワイプ候補の共有

- 課題: 一覧・詳細間の遷移による候補の再取得と状態消失
- 工夫: 共通Providerで候補キャッシュを共有し、成功時は対象だけをキャッシュから削除
- 効果: `/recs`内の画面遷移では再取得せず、同じカード位置を即時表示

## 画像表示の最適化

- 課題: 画像の転送量とレイアウトシフト
- 工夫: `next/image`と`sizes`を使用し、画面外は遅延読み込み、LCP候補は先行読み込み
- 効果: 表示幅に合う画像配信、LCP短縮、CLS防止

## k6負荷試験

- 認証フロー・WebSocketに対応できるためk6を採用(Vegeta等はリクエスト間の値の受け渡し不可)
- 発見: DBコネクションプールの上限未設定。負荷時にPostgres接続が枯渇

## プロフィール画像配信

- 課題: APIサーバーの画像転送負荷と、画像URL変更時のDB更新
- 工夫: presigned URLでストレージへ直接アップロードし、DBにはS3 keyだけを保存
- 効果: API負荷を抑え、配信ドメイン変更時のDB更新を不要化

## 検証環境の初回レスポンス改善

- 課題: コールドスタートとリージョン間通信による初回遅延
- 工夫: APIの常時起動、タイムアウト設定、Vercel FunctionとRenderのリージョン統一
- 効果: 初回アクセス時の待ち時間と長時間ブロックを削減

## メッセージ・マッチ一覧のキャッシュ設計

- WebSocket受信時にキャッシュを部分更新し、メッセージとマッチ状態を即時反映
- 全件再取得を避け、通信量とAPI負荷を抑えながらリアルタイムな操作感を維持
